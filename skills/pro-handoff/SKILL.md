# Pro Handoff

**只在用户明确要求时触发。** 这是一个主动行为：任务结束、会话变长、阶段完成或工作被中断本身都不构成触发条件，agent 不得自行判断“该交接了”而创建 `handoff/`。

在以下情况触发：

- 用户明确说 "写个交接 / handoff / 交棒 / 留个交接件 / 让下一个人接着做 / 停在这里，把状态写下来给别人"。
- 用户明确说 "按 handoff/ 接手 / 从交接件开始 / 接着上一个 agent 的活干"，要求以交接件为唯一起点开始工作。

不触发：

- 用户没有提到交接、handoff 或接手，即使当前工作正好停在设计完成、工单拆完或实现到一半。
- 只是让当前会话继续做下一步，没有角色切换或上下文断裂。
- 用户只是说 "先停一下 / 今天到这里"，没有要求把状态写给另一个角色。可以在回复中问一句是否需要交接件，但不主动创建。
- 要求压缩、总结或归档聊天记录，那是 `pro-memory` 的范围。
- 要求写长期可追踪的项目计划并维护索引，那是 `pro-plans` 的范围。

## 核心原则

1. **交接的是工件，不是对话。** 对话会腐烂，文件是唯一真相。接手者不会看到上一轮对话，也不该被要求去看。
2. **按角色分阶段交棒。** 设计者只交设计，规划者只交工单，实现者只交进度。交接件写清楚“我是谁、做到哪、你是谁、从哪开始”。
3. **接手者零上下文起步。** 交接件中的每一条事实都要能在仓库文件、命令输出或链接中重新核实；不能核实的写成“待确认”。
4. **一次性，不建索引。** `handoff/` 没有 README，也不进入 `plans/README.md` 或其他索引。交接完成即失效，长期知识另走 `plans/`、`docs/`、`.exp/`。
5. **不复制已有事实源。** 已在 `plans/`、`docs/`、`AGENTS.md` 中写清楚的内容只链接，不复述；交接件只补这些文档没有的部分：停点、状态、下一步、接手指令。

## 协同与互斥

- **与 `pro-plans` 区分**：`plans/` 是项目内长期可追踪的计划，有索引、有状态演进；`handoff/` 是一次性的交棒文件，无索引，交接完成即可归档或删除。已有计划时，交接件链接到计划，不重新写一份。
- **与 `pro-memory` 区分**：`.ai_memory/` 是项目级长期上下文，面向同一项目上的所有后续会话；交接件面向一个明确的接手角色和一个明确的起点。
- **与 `pro-exp` 区分**：交接过程中发现的可复用解法由 `pro-exp` 写入 `.exp/`，不塞进交接件。
- **与 `pro-summary` 区分**：`pro-summary` 审查文档一致性时不要求 `handoff/` 有索引，也不把它计入文档结构。
- **不扩大授权**：写交接件不等于授权接手者执行；接手者的授权来自用户在新会话中的指令。交接件中的“下一步”是建议路线，不是执行合同。
- **不自动触发**：其他 skill 或宿主规则不得因“任务结束”“上下文过长”而隐式调用本 skill；需要交接时由用户说出来。

## 一、目录约定

1. 交接件默认写在当前项目根目录的 `handoff/` 下，目录不存在则创建。
2. 简单交接用单文件：

```text
handoff/
└── YYYY-MM-DD-short-topic.md
```

3. 复杂交接（有独立 spec、多张工单或多阶段进度）用目录，`00-handoff.md` 是唯一入口：

```text
handoff/
└── YYYY-MM-DD-short-topic/
    ├── 00-handoff.md          # 入口：角色、停点、状态、接手指令
    ├── 01-spec.md             # 设计者交出的设计（可选）
    ├── 02-tickets.md          # 规划者交出的工单清单（可选）
    │   或 tickets/T01-xxx.md  # 工单多时拆成单文件
    └── 03-progress.md         # 实现者交出的进度与残留（可选）
```

4. 判断标准：一屏内能读完、且接手者只有一种角色，用单文件；否则用目录。不确定时先写单文件，膨胀后再拆。
5. 若仓库已有 `handoff/` 命名约定，沿用现状。
6. `handoff/` 不建 README、不建索引。同一主题多次交接时新建新日期文件，不覆盖旧文件。

## 二、三类停点

交接件必须声明停在哪一类停点，不同停点交出的工件不同：

| 停点 | 交出方 | 交出的工件 | 接手方从哪开始 |
|---|---|---|---|
| 设计完成 | 设计 / 架构角色 | spec：目标、非目标、接口、数据结构、约束、已排除的方案及原因 | 拆工单或直接实现 |
| 工单拆完 | 规划角色 | tickets：每张工单的范围、涉及文件、完成标准、依赖顺序 | 按顺序领第一张未完成工单 |
| 实现到一半 | 实现角色 | progress：已完成项（含文件路径与验证结果）、未完成项、残留的临时改动、当前验证状态 | 先复现当前验证状态，再继续未完成项 |

可以同时交出多类工件（例如设计完成时顺手拆了工单），但 `00-handoff.md` 里的停点只声明一个：最靠后的那个。

## 三、交接件内容

入口文件（单文件或 `00-handoff.md`）按以下顺序组织，模板见 `assets/handoff-template.md`：

1. **交接元信息**：日期、交出角色、接手角色、停点类型、状态标注。
2. **目标与非目标**：这一棒最终要做成什么，明确不做什么。
3. **当前事实**：已确定的决策、约束、不变量，每条附文件路径或命令。已在 `plans/` 或 `docs/` 中的只链接。
4. **已完成**：做到哪了，每项附可核实的证据（文件路径、commit、测试命令与结果）。
5. **下一步**：接手者应做的事，按顺序列出，第一条必须是接手者启动后立刻能做的动作。
6. **验证方式**：接手者完成后如何证明做对了，包括命令和预期结果。
7. **开放问题**：分成两栏，“接手者可自决”和“需要用户决定”，不混写。
8. **接手指令**：给接手者的直接指令，包括先读哪些文件、哪些不要动、哪些临时改动要清理、完成后如何收口。

工单文件（`02-tickets.md` 或 `tickets/T##-xxx.md`）每张至少包含：范围、涉及文件、完成标准、依赖的前置工单、状态。模板见 `assets/ticket-template.md`。

## 四、写作要求

1. 不引用对话：不写“如上所述”、“我们之前讨论过”、“用户说”。要写就把结论写出来并给出文件依据。
2. 路径写仓库相对路径，命令写完整可复制的形式，不依赖当前 shell 状态。
3. 已完成项必须附证据；没有证据的写进“未完成”或“待确认”，不写进“已完成”。
4. 残留的临时改动（调试日志、跳过的测试、硬编码、未提交文件）必须逐条列出，接手者不用猜。
5. 停点之后的设想只写成建议，不伪装成已决策。
6. 不写真实凭据、私密地址、本机绝对路径或个人信息。

## 五、状态标注

| 标注 | 含义 |
|---|---|
| `[ready]` | 交接件已写完，等待接手 |
| `[taken]` | 有人已按此交接件开始工作 |
| `[done]` | 这一棒已完成并验证，交接件失效 |
| `[stale]` | 仓库已变化，交接件内容与事实不符，需要重写 |

状态写在入口文件元信息中，由当前持有者更新。

## 六、接手流程

用户要求按 `handoff/` 接手时：

1. 只读 `handoff/` 中用户指定的交接件；未指定时取最新日期且状态为 `[ready]` 的一份。不去找上一轮对话，也不假设自己知道任何交接件之外的背景。
2. 逐条核实“当前事实”和“已完成”：引用的文件是否存在、命令是否得到声明的结果。核实不通过的项标记出来并告知用户，不基于错误事实继续。
3. 核实通过后把状态改为 `[taken]`，再按“接手指令”和“下一步”开始工作。
4. 需要执行的动作仍遵守宿主授权边界：交接件中的“下一步”不替代用户授权。
5. 自己也停下时，同样按本 skill 写新的交接件；完成时把状态改为 `[done]`，是否删除交接件由用户决定，默认保留。

## 七、输出要求

写交接件后，最终回复包含：

- 交接件路径（单文件或目录入口）。
- 停点类型与状态。
- 有哪些事实是“待确认”而非“已确认”。
- 需要用户在交接前决定的开放问题（如有）。

接手后，最终回复包含：

- 依据的交接件路径。
- 核实结果：哪些事实通过、哪些不符。
- 从哪一步开始继续，以及是否需要用户授权。
