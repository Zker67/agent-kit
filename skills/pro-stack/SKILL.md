# Pro Stack

为桌面软件、移动应用、网站/Web 应用及其配套后端，根据项目需求和 [技术偏好](./references/preferences.md) 提出有理由、可验证的选型建议。用户当前要求和项目已确认架构优先。

## 触发与边界

- 先判断本次交付物，再判断是否需要选型。只有交付物属于桌面软件、移动应用、网站/Web 应用或其配套后端，且技术路线待定或用户要求比较、调整架构时使用。
- 编写、修改或安装 Skill（包括本 Skill）、独立 MCP server/工具/插件、agent 配置、提示词、命令行脚本，以及 SDK/库、构建工具等工具链维护均在范围之外。即使这些任务包含“初始化”“技术栈”“架构”“框架”等词，或使用了 React、TypeScript 等候选技术，也不触发。
- 网站或应用接入 Skill、MCP 时，以本次交付物区分：选择应用技术栈属于本流程；仅实现 MCP server、修改 Skill 或配置连接不属于本流程。
- 已确定技术栈的日常开发、修 bug、更新依赖和只补文档不重新选型。现有产品只有在用户要求评估架构调整时重新选型，不因偏好与现状不同而建议整栈替换。
- 如果已经读取本 Skill，但任务属于范围之外，停止本流程，不读取技术偏好，不把 Web/桌面候选套入工具开发；回到任务适用的规则或对应 Skill。明确提到本 Skill 的维护任务也按维护处理。

## 1. 建立需求与约束

读取 `references/preferences.md`、当前任务、适用项目规则和已有技术决策。优先使用实际文件和用户已提供的信息，只补齐会改变选型的关键缺口：

- 产品形态与目标平台：网页、桌面、移动端，以及应用配套后端的运行环境；区分本版正式交付的平台与未来可能扩展的平台。
- 核心功能、现有代码、需要复用的组件或系统能力。
- 决定成败的 2–3 项关键能力，如富文本、系统集成、后台运行、复杂表格；它们优先于一般功能验证。
- 最值得复用的资产：已有 Web UI、业务逻辑、开发经验，或跨端统一的界面。
- 在线与离线、数据规模、多人访问与同步需求。
- 性能目标：启动、内存、响应速度、渲染或计算；缺少测量时不把框架标签当性能结论。
- UI 要求：标准组件是否足够，是否需要特别风格化或复杂动画。
- 开发维护能力、交付期限、部署条件与成本约束。

只分析时保持只读。信息不足但不阻碍初步建议时，标注假设继续；关键平台或不可替代能力未知时，给条件方案，并集中提出必要问题。

## 2. 形成最小可行方案

先判断既有技术栈是否已经满足需求。新项目按需求分别选择 UI、运行容器、后端、状态和数据层，不把候选清单当成必须全部安装的套餐。

- 偏好是取舍依据，用户明确要求和项目已确认决策优先；发现冲突时解释影响，不静默改动。
- 对每项选择说明适用条件；功能可以由现有能力满足时不增加依赖。
- 不把语言、构建工具、应用框架、数据库平台与数据访问工具当作同层替代项。
- 跨平台、组件复用和运行环境差异需要单独评估；桌面、Web、移动端不机械共用整套 UI 技术。
- 先判断是否需要独立 API 服务；应用框架的服务端能力或托管后端平台已满足需求时不提前拆分，独立部署、多客户端共用等需求明确后再拆。
- 多种语言的客户端共用同一后端时，评估用 OpenAPI 描述 HTTP 接口并生成各端客户端；单一 TypeScript 全栈项目可以直接共享类型，不额外引入。
- 超出偏好覆盖范围的项目走通用流程，不强行套入随附技术栈。
- 偏离用户偏好时，说明具体原因、收益和代价；仅在存在实质取舍时提供备选。

## 3. 按决策需要核验

依赖当前版本、平台支持、许可或兼容性的结论，应使用宿主可用的文档工具读取官方文档、发布说明或项目自身资料。偏好候选的官网与文档入口见 [官方入口索引](./references/docs.md)。遵循宿主的联网路由；已有可靠证据可复用。

- 偏好中的版本号只代表目标倾向，不证明已经发布、稳定或兼容。
- 建议前核对影响路线的关键限制；实施前核对实际依赖版本、插件、工具链和构建方式。
- 对性能、资源占用或交付成本的比较，区分官方描述、推断和实际测量。需要实测时提出最小原型与验收指标，只有获得执行授权后才运行。
- 无法联网或证据不足时明确待验证项，不编造确定结论，也不因此把可完成的需求分析停下。

## 4. 输出建议并处理协商

先给推荐路线与主要理由，再按项目复杂度说明组成和取舍。可使用紧凑表格：

| 层次 | 推荐 | 需求依据与偏好依据 | 限制或待验证项 |
|---|---|---|---|
| 与本项目有关的层次 | 具体选择 | 为什么需要、采用或偏离哪项偏好 | 当前证据与缺口 |

随后只列出影响决定的备选与待决问题。区分“建议方案”“用户确认的决策”“已验证可运行”，不要混写状态。

- 用户要求先协商时，在关键路线确定前完成可独立推进的读取和分析，再等待决定。
- 用户已经明确方案或授权按判断实施时，遵循既有授权继续，不重复索取同一确认。
- 建议本身不授权初始化、依赖安装、架构迁移、Git 写操作或部署。
- 只有用户要求保存决策或适用项目规则要求时才落盘。复用已有架构文档，记录选型理由、约束和验证状态；AGENTS.md 只保留必要不变量或入口，避免维护两份完整决策。

## 与其他 skill 的协同

- `pro-newproj`：创建文档骨架；仅当初始化的是本 Skill 范围内的软件产品且需要选型时，先提供建议。其他类型项目的初始化、技术栈已确定或只补文档时不转入本流程。不改通用项目模板来保存个人偏好。
- `pro-plans`：在用户要求计划落盘时维护实施计划；选型建议不默认创建 plans 文档。
- `pro-copy`：需要借鉴开源实现时提供来源与可复用思路；引用候选不等于决定技术栈。
- `pro-idea`：提出产品或工程改进建议；本 Skill 专注技术路线的取舍。
