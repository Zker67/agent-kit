# 作者个人技术偏好

这是 `pro-stack` 使用的技术偏好，来自作者个人的技术倾向。按下述条件提出建议，最终选择仍需结合项目需求。

## 使用原则

- 偏好按场景生效，需求与项目已确认架构优先。已有项目不因这份清单而自动升级或迁移。
- 开始新技术路线前先提出建议并协商；已经明确的决定无需再次确认。
- 只引入当前功能需要的组件。性能、美观、实现成本和维护成本共同影响选型。
- 下表的版本是作者提出的目标倾向，未在此声明发布状态或兼容性。实际选型时重新核对，保留偏好的技术与主版本方向，采用所选框架、SDK 与依赖共同支持的稳定版本并锁定依赖；移动端遵循所选 Expo SDK 等平台的兼容组合，不直接套用 Web 项目的版本要求。不能满足条件时说明偏离原因。
- 候选按路线分组。Web 与 React 路线中的组件、状态与交互库只用于 React 界面；Flutter、GPUI 等其他客户端路线的状态、路由与组件按需求另行选择，不套用 React 路线条目。
- “适用条件与例外”用于防止机械套用；没有替作者新增未表达的框架优先级。
- 各项候选的官网与文档入口见 [官方入口索引](./docs.md)，按下表同名领域查找；新增或调整候选时同步更新该索引。

## 技术候选

### Web 与 React 路线

| 领域 | 作者偏好 | 适用条件与例外 |
|---|---|---|
| Web 前端基础 | React 19 + TypeScript 7 + Tailwind CSS 4 | React 生态项目的目标组合；根据框架、依赖与构建链核验可用版本，不能直接假定整组兼容。 |
| Web 工程工具链 | Vite Plus（Vite+） | Vite 体系项目优先评估；与应用框架分别判断，使用 Next.js 等框架时保留框架自身的构建方式，不额外强塞另一套构建流程。已稳定运行的普通 Vite 项目可以保留，迁移收益单独评估。 |
| Web UI 组件 | shadcn/ui（Nova 风格） | 用于相应的 Web React 界面；组件源码拷入项目，可控、可改、不绑死，基于 Radix / Base UI + Tailwind，设计语言统一。Nova 偏紧凑（padding 更小），适合后台与数据密集型界面；它不是唯一最优解，需要宽松视觉的页面按设计需求选择风格。移动端和原生桌面 UI 分别选择适配的组件。 |
| 图标 | Lucide | Feather 的活跃维护版，线条风格统一、干净，支持 tree-shaking；与 shadcn/ui 配合使用。 |
| 动画 | Motion（原 Framer Motion） | React 界面需要过渡、手势、布局动画或弹簧动画时评估；声明式 API、生产使用广泛。简单状态过渡可由 CSS 完成时不增加依赖。 |
| 可调整分栏 | react-resizable-panels | 后台、IDE 风格等需要可拖动调整大小的分栏布局时使用；没有该交互时不引入。 |
| 拖拽 | dnd-kit | 需要排序、看板、拖放等交互时评估；模块化、可访问性好，相比 react-dnd 更轻量灵活。 |
| 服务端状态 | TanStack Query | 需要远程数据获取、缓存或同步时评估；不把它当成独立后端。 |
| 客户端状态 | Zustand | 需要共享状态时评估；API 极简、无需 Provider、按需订阅，适用于中小到中大型项目。局部状态足够时不增加状态库。 |
| Web 应用框架 | Next.js | 需要 React 全栈、服务端渲染、搜索可见性或服务端业务能力时优先评估。以客户端交互为主、已有独立 API 的后台、工作台和浏览器工具，评估 React + Vite+，按需加路由。Tauri 等桌面 Web 容器使用 SPA 或静态导出的前端，不承接 Next.js 的服务端运行能力。 |
| 内容网站 | Astro | 官网、博客、文档、内容展示与落地页优先评估；以内容和搜索可见性为主，需要交互的局部可嵌入 React 等组件。简单静态页面可选更轻的方案；需要 React 全栈或较多服务端业务时回到 Next.js 评估。 |

### 客户端路线

| 领域 | 作者偏好 | 适用条件与例外 |
|---|---|---|
| Web 技术桌面客户端 | Tauri / Electron | 沿用 Web 界面做桌面应用时比较，不预设固定优先级。重视分发体积、愿意处理 Rust 与系统 WebView 差异时优先评估 Tauri；依赖 Node.js 能力、特定 Chromium 行为或已有 Electron 生态集成时优先评估 Electron。Tauri 2 也支持 Android 与 iOS，复用 Web 界面同时覆盖手机时同样参与比较。资源占用与响应速度按应用负载评估，不凭框架名称判断。 |
| 高性能原生桌面 | GPUI + GPUI Kit | 桌面是主要产品平台且满足下节条件时优先评估；GPUI Kit 指 longbridge/gpui-kit，不等同于其他同名或近名项目。`gpui-kit` crate 锁定匹配的 GPUI 版本并重新导出 GPUI 与组件库，版本在选型时确认。其移动端支持仍为实验性，不作为完整的移动应用方案。 |
| 移动端 | Expo + React Native | 以移动端为主、希望沿用 React / TypeScript 经验时的偏好路线；单独评估目标系统、原生模块、发布与 UI 组件需求。需要桌面覆盖时，不默认 Expo 项目已具备完整桌面能力，按目标平台单独核对，并与 Flutter 比较。 |
| 跨平台客户端 | Flutter + Dart | 桌面与移动端都重要、希望复用大部分 UI 与业务逻辑时优先评估；Web 不是主要交付渠道，或 Web 也是应用型界面时尤其适合。官网、博客、帮助中心等内容型网站单独选择 Web 技术。先按目标平台核对关键插件（如托盘、全局快捷键、后台任务、蓝牙、音视频、富文本），桌面的键鼠、窗口尺寸与手机触控分别设计。会引入 Dart 与另一套组件生态，现有 React 组件不能直接沿用。 |

### 数据

| 领域 | 作者偏好 | 适用条件与例外 |
|---|---|---|
| 轻量数据 | JSON | 配置、静态数据、导入导出，以及读写可控的小规模单用户数据。按使用方式而非数据量判断：数据量小但需要关联查询、频繁修改、事务或一致性约束时改用数据库。 |
| 浏览器本地结构化数据 | IndexedDB | 网页离线数据、较多结构化数据与本地索引查询时使用；少量简单键值可用 Web Storage。跨设备同步另行设计。 |
| 应用本地结构化数据 | SQLite | 桌面与移动应用的本地持久化、查询与事务候选；多设备或多人同步需求需另外设计。 |
| 服务端共享结构化数据 | PostgreSQL，结合 Supabase / Drizzle | 网页、移动与桌面多客户端共享数据的主要候选，不限于网页。PostgreSQL 是数据库；Supabase 是围绕它提供认证、存储、API、实时等能力的托管平台；Drizzle 是 TypeScript 环境的数据访问、结构定义与迁移工具。三者分别判断、按需组合；Flutter 等非 TypeScript 客户端通过 Supabase 对应 SDK 或后端 HTTP API 接入，Drizzle 留在 TypeScript 后端。 |

## 客户端路线分工

选择客户端路线，主要是在选择复用什么：

| 主要复用 | 优先评估 |
|---|---|
| 同一套界面组件与交互，同时覆盖桌面和手机 | Flutter |
| 已有 Web 页面、CSS、shadcn/ui 与浏览器生态能力 | React + Tauri / Electron；Tauri 2 可同时覆盖手机 |
| React / TypeScript 经验与业务逻辑，移动端是重点 | Expo + React Native |
| 以桌面为核心，标准而精致的组件能满足需求，重视资源与交互性能 | GPUI + GPUI Kit |

这是选型起点，最终取决于关键能力在目标平台上是否有可用实现。共享 UI 前确认两端产品形态足够相似：手机以浏览和轻操作为主、桌面是复杂多窗口工作台时，共享界面的收益下降。

## GPUI 路线的明确偏好

> 当标准化、精致的原生 UI 足够满足产品需求时，优先评估 GPUI + GPUI Kit 这条高性能技术路线。

适用倾向：桌面是主要产品平台，应用以基础功能和标准交互为主，对运行效率、资源占用或响应速度有较高要求；标准组件与布局能够满足需求，不需要特别风格化的视觉设计。

“不需要特别风格化”仍要求美观、精致和良好的交互体验，不意味着界面可以简陋。性能优先也不意味着仅凭框架名称认定更快。

选型时需确认：

- 目标平台支持，尤其是 Windows 上所需功能与交付方式。
- 组件覆盖、输入交互、系统集成、无障碍与打包要求。
- Rust 实现与维护成本，以及实际的性能证据。
- 是否需要复用已有 Web UI；采用原生 UI 路线时，重新评估 UI 与状态实现，不假定可以直接沿用 Web 组件。

这些条件不足时，比较 Tauri / Electron、Flutter 或其他符合需求的路线，说明取舍，不盲目选择 GPUI。
