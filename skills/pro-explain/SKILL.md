# Pro Explain

帮助用户建立能够预测实际行为的心智模型，而不是把源码逐行翻译成中文。解释应回答：它解决什么问题、从哪里开始、数据和状态怎样变化、为什么这样设计、失败时会发生什么。

## 边界

- 保持只读：允许检查源码、配置、测试、日志、错误栈和运行结果，但不修改代码、不添加注释、不创建文件。
- 用户同时要求解释和修改时，解释阶段仍按本方法确认当前行为；实际修改进入对应实现流程，不把解释自动升级为改动授权。
- 默认使用简体中文解释，代码标识符、命令和外部专名保持原文。
- 只解释当前问题所需的范围，不主动扩展成重构评审、完整教程或替代方案设计。

## 工作方法

### 1. 明确用户真正想理解什么

先判断问题的主体和深度：

- **代码或流程**：重点解释入口、调用顺序、数据变化、分支和副作用。
- **任务或方案**：重点解释目标、范围、输入、约束、步骤和成功标准。
- **报错**：重点解释预期行为、实际现象、第一个失败边界、传播路径和影响。
- **架构关系**：重点解释组件职责、依赖方向、数据归属、边界和失败路径。
- **技术概念**：重点解释它解决的问题、最小机制、在当前代码中的对应位置和适用限制。

信息不足但不影响核心含义时，说明假设并继续；缺失信息会改变结论时，只问一个最关键的问题。

### 2. 收集最小充分证据

1. 从用户指定的文件、错误信息或入口开始，读取直接相关的源码、配置、测试和日志。
2. 需要理解调用关系时，向上找到触发入口，向下找到关键依赖和最终输出；不要为局部问题通读整个仓库。
3. 优先引用真实文件路径和符号名；行号只有在当前已核对且确实有帮助时才使用，避免把易漂移的行号当成主要定位方式。
4. 静态源码只能证明可能的执行逻辑，不能单独证明某段代码已在真实环境运行；运行态结论需要日志、测试或实际输出支持。

### 3. 先建立模型，再组织语言

根据对象选择最合适的解释骨架：

- **调用链 / 数据流**：触发条件 → 输入 → 校验或转换 → 状态与依赖 → 分支或错误 → 输出与副作用。
- **报错链**：预期结果 → 实际现象 → 第一个失败边界 → 错误如何向上传播 → 用户最终看到的报错。不要把最后一层异常自动当作根因。
- **架构关系**：每个组件负责什么 → 谁调用谁 → 数据由谁拥有 → 边界在哪里 → 某一层失败会影响谁。
- **技术概念**：先用一句大白话说明用途 → 再讲最小工作机制 → 映射到当前代码 → 最后说明限制和常见误解。

解释 `if`、循环、类型或语法细节，只在它们会改变当前行为时展开；不要把每一行代码都重复描述一遍。

### 4. 面向初学者表达

- 先讲整体，再讲局部；先讲“发生了什么”，再讲“为什么这样做”。
- 术语首次出现时用通俗中文解释，并保留原始英文名称，例如“依赖注入（Dependency Injection）”。
- 优先使用当前代码里的真实变量、数据或请求作为例子，避免另造一个更难理解的示例系统。
- 类比只用于降低理解门槛，并说明类比在哪些地方不成立，避免用户把类比当成真实实现。
- 把长流程拆成少量有因果关系的步骤；必要时使用小表格或简单流程图，不为排版强行增加结构。
- 引用代码时只摘取支撑解释的短片段，不大段复制用户已经能看到的源码。

### 5. 标明证据强度

解释中保持以下区分；简单问题不必机械加标签，存在歧义时再显式标注：

- **已确认**：可由源码、配置、测试、日志或运行结果直接证明。
- **合理推断**：证据支持，但仍依赖未核对的调用方、环境或运行条件。
- **尚未确认**：缺少必要文件、配置、输入、日志或真实运行证据。

不要使用“应该是”“大概”掩盖证据缺口；说明缺少什么，以及它会不会改变当前结论。

## 输出组织

选择能最短讲清问题的结构，不强制所有回答套同一个模板：

- **简单概念**：一句话结论 → 通俗解释 → 当前场景中的例子。
- **代码或流程**：一句话结论 → 执行顺序 → 关键状态、分支与副作用 → 边界。
- **报错**：现象 → 根因或首个失败边界 → 错误传播 → 影响与未确认项。
- **架构**：整体关系 → 各组件职责 → 一次完整请求或数据流 → 边界与失败路径。

复杂解释结束前做一次自检：用户是否已经能回答“谁触发它、输入是什么、关键状态怎样变化、什么时候失败、最终输出或影响是什么”。若某项与当前问题无关，不必为了完整而补写。

## 避免这些解释方式

- 逐行翻译代码，却不说明整体目标和执行关系。
- 只复述错误文本，未定位第一个失败边界。
- 根据命名、注释或目录结构推断运行态，并把推断写成事实。
- 用更多术语解释术语，或一次引入过多抽象层。
- 混淆“当前实现是什么”“为什么这样设计”和“应该怎样改进”。
- 在用户只想理解时附带未经请求的重构方案、代码修改或文件写入。
