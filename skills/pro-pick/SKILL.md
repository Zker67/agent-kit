# Pro Pick

**只由用户主动触发，AI 不得被动触发。** 触发条件只有两种：用户明确说“让我来选”一类的话，或用户点名 `pro-pick`。素材主观、方案难定、改动需要人看一眼，这些情境本身都不是触发条件；即使情境完全吻合，用户没说就不启动，也不主动推荐走陈列流程。

触发：

- 用户点名：“用 pro-pick”“走 pro-pick 流程”。
- 用户明确要求由自己选：“让我来选”“摆出来我挑”“给我几个候选我来定”“做个能预览的页面我来选”。
- 用户把一份 `result.json` 交回来，说“按我选的接入 / 打回的再找”。这是上一次触发的延续。

不触发：

- 用户没有说“让我来选”也没有点名 `pro-pick`，只是要求实现、接入、自测、或“做出来给我看看”。
- 用户已经指定了具体素材或方案，只需要直接接入。
- 用户要求 AI 自己评估哪个更好并直接用。本 skill 不做这件事；按普通实现处理，不反问是否要走陈列流程。

## 核心原则

1. **AI 只负责记点、取材、陈列。** 记点：哪些位置需要人拍板；取材：为每个位置收集候选；陈列：摆进一个人能看、能播、能勾、能批注的页面。
2. **判断权在人。** 候选的事实字段里不夹带结论，不排序，不标推荐。AI 若有想法，只能写进单独的 `suggestion` 字段，页面上以“AI 建议”标出，与事实分开；它是参考，人可以无视。
3. **交付物是 HTML，不是对话回复。** 陈列页面本身就是给人的成果；对话里只说路径和怎么交回 JSON，不逐条复述候选内容。
4. **候选可以是任何形式。** 图片、音频、视频、可在框中打开的 HTML 片段、纯文本，都是候选；截图也是候选的一种。一个接入点可以只有一个候选，此时人的操作退化为“通过 / 打回”。
5. **人选定后再动手。** 没有 `result.json` 之前，不正式接入任何候选。
6. **可迭代。** `result.json` 中打回（`more`）的接入点进入下一轮：AI 按批注补充新候选，生成新一轮陈列，直到人不再打回或明确说停。

## 协同与互斥

- **与 `pro-handoff` 区分**：交接件是给下一个 agent 看的文字工件；陈列页面是给人看的视觉工件。两者都不建索引、都是一次性的，但读者不同。
- **与 `pro-plans` 区分**：陈列的是待选的候选，不是计划。若人选完后需要大改方案，改动方案交给 `pro-plans`。
- **与 `pro-exp` 区分**：取材和接入过程中发现的可复用经验由 `pro-exp` 写入 `.exp/`。
- **与宿主浏览器 / 截图 / 生成工具的关系**：本 skill 不固化具体工具。按宿主实际提供的能力（浏览器 MCP、Playwright、图像或音频生成工具、公开素材库）取材；某类候选无法取得时如实在条目里标明。
- **不扩大授权**：接入素材、修改代码仍遵守宿主授权边界；`result.json` 表达了用户意图，但涉及生产、删除、外部发布的动作仍需按宿主规则确认。
- **不被其他 skill 或规则隐式调用**：宿主全局规则、其他 skill、或 AI 自己的“这里最好让人选”判断都不能启动本 skill。

## 一、目录约定

1. 所有产物写在当前项目根目录的 `pick/` 下，目录不存在则创建。每次陈列一个目录，不建索引：

```text
pick/
└── YYYY-MM-DD-short-topic/
    ├── manifest.json        # AI 写：接入点、候选、媒体路径、事实描述
    ├── index.html           # 由 assets/gallery-template.html 生成，内嵌 manifest
    ├── media/               # 候选文件或其预览
    ├── result.json          # 人给：选择与批注
    └── round-2/             # 迭代时新建，结构同上
```

2. `index.html` 必须能以 `file://` 直接双击打开：单文件、无外部依赖、manifest 内嵌在 `<script type="application/json">` 中、媒体用相对路径。
3. 媒体文件可能较大。若项目不希望把它们进入版本库，提醒用户把 `pick/` 加入 `.gitignore`，但不要自行修改 `.gitignore`。
4. 若仓库已有不同约定，沿用现状。

## 二、流程

**记接入点**

1. 为每个需要人拍板的位置记一个 slot：`name`、`scene`（用在哪、用户在什么情境下看到或听到）、`constraints`（尺寸、时长、格式等硬约束，只写硬约束）。
2. 只记名字和场景，不预设“应该选什么风格”。
3. 用户要求“先做出来给我看”时，把要看的位置也记成 slot，候选就是做出来的那一版（截图、页面片段或文本）。

**取材**

1. 每个 slot 收集候选。要人挑的通常 2 到 5 个；要人点头的可以只有 1 个。
2. 候选来源可以是项目已有资产、生成工具产出、公开素材库、当前实现的截图；每个候选记 `source`（来源）与 `license`（许可，不确定写 `unknown`）。
3. 布局、配色、文案这类非文件素材，做成可在 `iframe` 中独立打开的 HTML 片段或纯文本候选。
4. 同一 slot 的候选保持可比：尺寸、时长、命名方式一致，方便并排看。
5. 不排序、不标推荐；顺序按收集顺序或字母序。AI 有倾向时写进 slot 级 `suggestion`。
6. 全部 slot 取材完成后再陈列，不分批。

**陈列**

1. 用 `assets/gallery-template.html` 生成 `index.html`，协议见 `assets/protocol.md`。
2. 页面上每个 slot 一个单位：名字、场景、约束、AI 建议（若有）、候选并排（图片可放大、音视频可播放、HTML 可在内嵌框中查看、文本内联）、操作区。
3. 人对每个 slot 做一件事：选一个候选，或点“都不要，再找”；可写批注（例如“要再暗一点”“节奏慢一些”“间距改回 8px”）。
4. 页面底部一键导出 `result.json`，人放回目录或把内容贴回对话。

**接入与迭代**

1. AI 读取 `result.json`：有 `chosen` 的 slot 按项目实际方式正式接入（复制到资产目录、写引用、更新配置、应用改动）；`more` 的 slot 按批注补充新候选。
2. 有 `more` 时生成 `round-2/`，只包含被打回的 slot，`id` 沿用，候选重新取材；已选定的不重复陈列。
3. 一轮 `result.json` 中没有 `more` 即结束，或用户明确说停。

## 三、写作要求

1. 事实字段（`name`、`scene`、`constraints`、`label`、`source`）只写事实：这是什么、用在哪、从哪来。评判词只允许出现在 `suggestion` 字段里。
2. 候选 `label` 描述该候选本身（“钢琴慢板，90 秒”），不描述它相对其他候选如何。
3. 路径写相对路径，命令写完整可复制形式。
4. 来源与许可如实记录；不确定的写 `unknown`，不写“应该可以用”。
5. 不在 `manifest.json` 或页面中写入真实凭据、私密地址、本机绝对路径或个人信息。

## 四、收尾

1. 每一轮一个子目录（`round-2/`、`round-3/`），不覆盖上一轮，人可以回看历史选择。
2. 收尾时告知用户：哪些 slot 已接入到哪里、哪些仍被打回未处理。`pick/` 目录是否删除由用户决定，默认保留。

## 五、输出要求

生成陈列后，对话回复保持简短，成果在 HTML 里：

- `index.html` 的路径与打开方式（直接双击或用浏览器打开）。
- slot 数、候选总数、本轮次。
- 哪些 slot 候选不足或无法取材，以及原因。
- 一句话说明如何把 `result.json` 交回。
- 不在对话里逐条描述候选或复述建议。

读取 `result.json` 后，最终回复包含：

- 每个 slot 的处理：接入到哪 / 补了几个新候选 / 保留未动。
- 是否生成了下一轮，路径在哪。
- 需要用户授权才能继续的动作（如有）。
